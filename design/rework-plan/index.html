    MLArray / MedVol rework — process and handoff¶

    This document lets any agent or developer continue the rework without prior context. Read it fully before touching code. Keep it current: when a stage step is done, tick it and add the commit hash.

    0. Orientation¶

    What the rework is¶

    1. MLArray gets a new metadata model: domain-neutral core + profiles + readable source + user, plain msgpack, explicit geometry.
    2. MedVol becomes a faithful N:N converter built on that model.
    3. Before that, the existing storage and array code is cleaned up and its known bugs are fixed, without changing user-facing behaviour or storage optimisation.

    Working rules (from the user)¶

    • Commit after every sensible, complete, working change. Use separate, focused commits per logical change.
    • Commit messages and docs must not mention AI, Claude or any assistant, and must not contain Co-Authored-By trailers.
    • Don't push unless asked.
    • No backwards compatibility with v0 .mla files and no migration code.
    • No de-identification and no other modification of metadata.
    • Functionality, user-facing usage and storage optimisation must not change in stages 1–2. Any bug fix that changes observable behaviour must be listed in §6 and confirmed by the user before it lands.
    • Invariant through all stages: tests/test_layout.py and tests/test_read_ahead.py stay unchanged and green (one agreed exception: in stage 3, test_layout.py's metadata accessors change, see §3). They pin the storage defaults:
    • the nnU-Net chunk/block heuristic in mlarray/blosc2_layout_strategies.py;
    • LZ4HC level 5 with 4 compression threads, and nnU-Net's per-array filter choice;
    • blosc2 read-ahead with 4 threads, switched on by the first MLArray.open (mlarray.set_read_ahead()).

    5. After the stages¶

    The follow-up work (consumers, MedVol release, CD notes) is tracked in docs/design/followups.md.

    • SlicerMLArray and napari-mlarray read the v1 core. napari should use the axis-order recipe from KB ch06 §6.3 for correct on-screen orientation.
    • Pyramids (spec §4.6, storage still to design) and lazy or streaming IO are later versions.
    • Non-medical format plugins (OME-TIFF, FITS, GeoTIFF) are later; the model already covers them (spec §5.3).
